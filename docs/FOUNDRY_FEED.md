# Foundry live feed

The mesh gateway can queue every valid version-2 telemetry packet before updating its latest-packet API. The dashboard writes activity, baseline, location, and alert events to the same SQLite outbox. Only the gateway publishes; no Foundry request occurs in a sensor read or local alert. The dashboard remains the operator interface.

## Local setup and mock verification

Run the two processes from the repository root with the same outbox path and `--mesh-node` names:

```powershell
.venv\Scripts\python.exe dashboard\mesh_api.py --serial-port COM11 --mesh-node Wearer1=206EF1316774 --mesh-node Wearer2=206EF1316838 --foundry-outbox .foundry-outbox\outbox.sqlite3
.venv\Scripts\python.exe dashboard\server.py --mesh-api http://127.0.0.1:8766/api/nodes --mesh-node Wearer1=206EF1316774 --mesh-node Wearer2=206EF1316838 --foundry-outbox .foundry-outbox\outbox.sqlite3 --replay= --synthetic 0
```

`GET /api/nodes` includes `foundry`: queued records, serialized payload bytes, age of the oldest record, dropped count, failed local writes, publishing state, last successful publish, and error. The dashboard system log reports that state at startup, after errors or drops change, and every minute. With no credentials, the local queue runs but publishing remains off. The outbox expires unsent records after one hour and evicts oldest records above 100 MB of serialized payload; SQLite file and WAL overhead may use additional disk space. `dropped` counts expiry and capacity eviction; `write_failures` counts gateway packets that could not enter the outbox. Keep the outbox under a user-restricted directory; it contains names, heart rates, and location estimates.

Run the local mock OAuth and stream tests before connecting an enrollment:

```powershell
.venv\Scripts\python.exe -m unittest tests.test_foundry_bridge -v
```

## Foundry streams

Create two streams on the `master` branch with these nullable fields except for `event_id`, `node_id`, and the time field. Set `event_id` as the stream key. Publisher retries retain the same ID; downstream consumers should deduplicate by it because a response may be lost after Foundry accepts a batch.

| Telemetry field | Foundry type |
| --- | --- |
| `event_id`, `node_id`, `wearer_name` | String |
| `received_at_ms`, `root_received_ms`, `sequence`, `uptime_ms`, `steps` | Long |
| `schema_version`, `hop_count` | Integer |
| `sensor_ok`, `hr_valid`, `wake` | Boolean |
| `hr_bpm`, `accel_x_m_s2`, `accel_y_m_s2`, `accel_z_m_s2`, `gyro_x_rad_s`, `gyro_y_rad_s`, `gyro_z_rad_s`, `yaw_delta_rad`, `imu_temp_c` | Double |

| Event field | Foundry type |
| --- | --- |
| `event_id`, `session_id`, `node_id`, `wearer_name`, `event_type`, `activity`, `alert_id`, `alert_kind`, `alert_state`, `alert_severity`, `reason`, `location_source`, `location_quality` | String |
| `observed_at_ms`, `alert_cleared_at_ms` | Long |
| `baseline_bpm`, `lat`, `lon` | Double |

Telemetry uses laptop receipt time and preserves device uptime and sequence. Event location is an IMU estimate or operator correction, not GPS. `session_id` distinguishes dashboard restarts; `event_id` is a UUID generated by the outbox.

## Foundry activation

Create a Developer Console backend service with application permissions, grant its service user write access to both streams, and allow the stream-write operation. Configure security markings, project access, and retention for identifiable health and location data before enabling real publishing. Foundry's [push guide](https://www.palantir.com/docs/foundry/data-connection/push-based-ingestion) describes the service application and stream setup; the [publish API](https://www.palantir.com/docs/foundry/api/streams-v2-resources/streams/publish-records-to-stream) specifies the batch endpoint.

Set these environment variables in the **gateway process** only, then restart it:

```text
FOUNDRY_HOST=https://your-enrollment.palantirfoundry.com
FOUNDRY_TELEMETRY_RID=ri.foundry.main.dataset....
FOUNDRY_EVENTS_RID=ri.foundry.main.dataset....
FOUNDRY_CLIENT_ID=...
FOUNDRY_CLIENT_SECRET=...
```

The publisher requests short-lived OAuth client-credentials tokens and sends batches of up to 100 records per stream. The default requested scope is `api:use-streams-write`; set `FOUNDRY_SCOPE` if the enrollment's application restrictions require a different stream-write scope. Never put the secret in a command line, browser, or tracked file. On HTTP failures the queue is retained until acknowledged or aged out; a rejected schema batch remains queued and is reported as an error until corrected or expired. Verify synthetic records in both streams before using real wearer data.
